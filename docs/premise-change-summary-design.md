# 种子修改摘要设计

日期：2026-10-23  
状态：已实施（2026-10-23）  
适用范围：已有「按建议修改」能力的增量增强

## 1. 目标

作者提交建议后，先看到「哪些内容被修改、具体如何变化」，再阅读完整候选种子，减少通读原稿和候选、凭记忆比较的成本。

推荐方案：在同一次 AI 修改生成中输出完整候选和简短修改说明；后端通过正式种子与候选的字段比对，确定真实改动列表，再将说明绑定到对应改动。前端在完整候选之前展示「本次修改」。

本次只设计修改摘要，不扩展为历史版本管理、候选上的连续调整、逐项采用、自动采用或逐字差异编辑器。已有采用、回退、下游失效、执行互斥和失败保留语义继续沿用。

## 3. 用户交互

卡片仍位于种子页面最下方。成功后的阅读顺序为：

1. 用户输入的修改建议与生成按钮。
2. 「本次修改」：变更项数、中文字段标签、每项简短修改说明。
3. 每项可展开的修改前后原文。
4. 完整候选种子。
5. 现有「采用修改」「放弃」操作。

示例：作者输入「增加男女互动情节」。

> **本次修改 · 3 项**
>
> **一句话梗概**：补充男女主因纪录片拍摄被迫合作的关系起点。
>
> **核心冲突**：增加公开采访素材与保护对方隐私之间的矛盾。
>
> **故事发动机 / 压力升级**：补充共同寻找证人、互相隐瞒线索的递进事件。
>
> 每项均可展开「查看修改前后」。

示例仅说明展示方式，不预设模型一定会修改这三个字段。实际页面必须以本次候选的真实变化为准。

```text
+------------------------------------------------------+
| Feedback                                             |
| [ Generate preview ]                                 |
|                                                      |
| Changes (3)                                          |
| * Logline      Short explanation                     |
|   [ Before / After ]                                 |
| * Conflict     Short explanation                     |
|   [ Before / After ]                                 |
| * Escalation   Short explanation                     |
|   [ Before / After ]                                 |
|                                                      |
| Full candidate                                       |
| ...                                                  |
| [ Adopt ] [ Discard ]                                |
+------------------------------------------------------+
```

### 展示细节

- 默认展示修改项名称与说明，前后原文折叠，避免长内容淹没摘要。
- 超过 5 项时先展示前 5 项，提供「展开其余 N 项」；总数始终包含全部变化。
- 采用现有卡片、文字和间距样式；通过文字标识「修改前」「修改后」，不只依赖颜色。
- 展开项使用可键盘操作的按钮或 Ant Design Collapse，并提供明确的可访问名称。
- 不显示 JSON 路径给作者，使用「主角 / 缺陷」等中文标签。
- 摘要只描述当前正式种子到本次候选的变化，不和上一份未采用候选比较。
- 采用前的影响确认仍说明下游失效，与本次内容摘要分开展示。

## 4. 修改事实与文字说明

### 4.1 后端确定真实修改项

不直接把模型声称修改过的字段作为最终清单。后端持有本次生成所用的正式种子快照，候选生成完成后逐字段比较；前后原文均取自这两个结构化对象。

| 分组 | 比较路径 |
| --- | --- |
| 故事概要 | `title`、`logline`、`theme`、`coreConflict`、`hook` |
| 故事发动机 | `storyEngine.openingGoal`、`storyEngine.mainObstacle`、`storyEngine.failureCost`、`storyEngine.escalationPath` |
| 主角 | `protagonist.name`、`protagonist.identity`、`protagonist.desire`、`protagonist.flaw` |
| 背景 | `setting.era`、`setting.place`、`setting.socialBackground` |
| 避雷 | `taboos` |

共 17 个比较单元。输出按上述分组固定排序，同一字段只计一次。

比较规则：

- 字符串按结构化对象中的实际文本比较，不做语义相似度判断；纯标点或空白改动也列入，不宣称能识别「实质改动」。
- 数组按元素内容和顺序比较，一个数组字段计一项，不按每个元素重复计数。
- 数组前后值完整保留；前端用列表展示，首版不计算数组元素的新增、删除或移动匹配。
- 历史种子缺少 `storyEngine` 时，新增的四个子字段分别计入，修改前显示「原种子未提供」。
- 类型、篇幅、基调、视角不属于种子产物，不进入修改清单，也不允许借本功能更改问卷。
- 文本比对只能确认内容变化，不能证明建议已被满足或作品质量提高。

### 4.2 AI 提供可读说明

AI 对修改项输出一条简短的「改了什么」说明，例如「将偶遇改为共同采访，引入需要持续合作的互动场景」。不要求输出内部思考过程，也不要求宣称建议已经全部落实。

后端按真实变化过滤说明：

- 模型报告了未变化字段：丢弃该条说明，不显示为变化。
- 字段确实变化但模型漏报：补入真实变化项，使用「已调整此处内容，可展开查看修改前后」作为中性说明。
- 同一字段重复报告：只保留第一条有效、非空说明。
- 不接受模型提供的修改前后原文作为事实来源。
- AI 说明属于辅助解读，可能不够准确；展示轻量说明「修改说明由 AI 生成，展开可核对实际变化」。

不额外发起第二次模型调用来生成摘要，避免新增一次延迟与计费。字段比对使用普通代码，模型调用仍走现有注册表、结构校验和用量记录。

## 5. 共享契约建议

下面是拟新增的类型形状，实施时先在 `shared/src/index.ts` 定义对应 zod schema 与推导类型。

```ts
// 值只能来自上表中固定的 17 个字段路径。
type PremiseChangePath = /* 固定字段路径联合类型 */ string;

type ChangeValue = string | string[] | null;

// AI 同一次调用的输出；不作为对外最终差异清单。
type RevisedPremiseOutput = {
  premise: GeneratedPremise;
  changeNotes: Array<{
    path: PremiseChangePath;
    description: string;
  }>;
};

// 对外返回，由后端真实比对生成。
type PremiseChangeSummary = {
  version: 1;
  changes: Array<{
    path: PremiseChangePath;
    before: ChangeValue;
    after: ChangeValue;
    description: string;
    descriptionSource: 'ai' | 'fallback';
  }>;
};

type PremisePreview = {
  candidateId: string;
  premise: GeneratedPremise;
  changeSummary: PremiseChangeSummary | null;
};
```

约束：

- 路径使用 `z.enum`，不能实现成接受任意字符串的 schema；上述 `string` 只用于省略联合类型的示意。
- 说明 trim 后为 1 至 120 字符，单次模型说明最多 17 项；`changeNotes` 缺失可按空数组处理。
- 后端生成的摘要路径唯一、数量不超过 17，且每项 `before` 与 `after` 不同。
- `null` 仅表示历史种子对应值缺失，不混同空字符串或空数组。
- 中文标签在前端维护固定映射，不允许模型自造字段名。
- 项数直接由 `changes.length` 计算，避免单独的计数字段与清单不一致。
- API 读取时可将历史缺失的 `changeSummary` 归一化为 `null`；新生成结果必须包含完整摘要对象，零改动时为 `changes: []`。

现有请求体和采用请求体保持不变；只扩展预览响应，不增加新的前端请求。

## 6. 后端与存储

### 6.1 生成流程

```text
Formal seed snapshot + questionnaire + feedback
                         |
                         v
                One structured LLM call
                         |
                         v
                Candidate + change notes
                         |
                         v
               Compare actual field values
                         |
                         v
             Verified paths + before / after
                         |
                         v
          Save candidate and summary in one transaction
```

1. 仍先校验正式种子、问卷与项目运行状态，按现有机制领取执行权。
2. 读取正式种子快照；生成输入、实际比对和 `baseHash` 对应同一份内容。
3. 使用注册模板 `premise-revision/v2`，按新的包裹 schema 一次生成候选及说明。
4. 校验完整候选，执行字段比对，过滤说明并补齐漏报字段。
5. 在现有持锁事务内同时写入候选、摘要、请求状态与用量。
6. 返回相同候选 ID 下的完整预览包；后端或前端均不得单独提前更新摘要。

模型包裹结构无法校验时沿用现有结构化修复和失败处理；语义层面的漏报、重复报告或报告未变化字段，由后端过滤与中性说明兜底，不单独触发新的模型调用。

### 6.2 数据结构与兼容

在 `PremiseRevision` 增加 `changeSummaryData String?`，保存经过服务端整理的 `PremiseChangeSummary` JSON 字符串。现有 `data` 继续只保存种子，避免影响采用接口中的 `PremiseSchema.parse`。

- 候选与摘要在同一事务写入成功；任一持久化失败均不替换上一份成功预览。
- 按请求 ID 重复查询时直接返回已保存的摘要，不重新调用 AI，不用当前正式种子重新计算旧摘要。
- 历史记录的新字段为 `null`，不批量回填、不追加模型调用。
- 历史候选预览显示「此候选生成于修改摘要功能上线前，暂无修改说明」；仍可按既有规则采用。
- 采用仍只读取并校验候选种子，不将摘要写入正式 `Premise.data`，也不传入下游创作上下文。
- `baseHash` 校验仍负责拒绝过期候选；摘要不取代该校验。
- 摘要读取若损坏，返回 `changeSummary: null` 并明确提示摘要不可用，保留合法完整候选；新生成记录必须先通过摘要 schema 再落库。

## 7. 状态与异常

| 场景 | 预期行为 |
| --- | --- |
| 首次生成成功 | 同时显示修改摘要与完整候选 |
| 再次生成中 | 保留上次摘要和候选，标注正在生成新预览，禁用冲突操作 |
| 再次生成失败 | 保留本次输入、上次摘要与候选，显示错误并可重试 |
| 完整候选与正式种子完全相同 | 摘要显示「本次未检测到字段变化，可调整建议后重试」，不伪造修改说明 |
| AI 漏报或夸大修改 | 按真实变化补全或过滤，不影响完整候选展示 |
| 用户继续编辑建议但未生成 | 已显示摘要仍属于原候选，不随输入变化更新 |
| 放弃候选 | 一起清除该候选及摘要，保留建议输入 |
| 采用成功 | 一起移除未采用预览与摘要，刷新正式种子和下游状态 |
| 采用失败或版本冲突 | 保留摘要与候选供查看，展示真实错误，不误报采用成功 |

零变化时首版不额外改变既有采用接口的行为；摘要提示只帮助作者判断，不引入新的确认或推进分支。

## 8. 验收标准

1. 作者生成修改预览后，无需先通读完整候选，即可看到实际修改的中文字段和简短说明。
2. 每个变化项都可展开修改前后原文，实际未变化的字段不出现在列表中。
3. 覆盖标题、故事概要、故事发动机、主角、背景、避雷共 17 个比较单元；数组整体计数，顺序变化可识别。
4. AI 漏报的变化仍出现；虚报的未变化字段不出现；真实差异的覆盖率为 100%。
5. 候选、摘要、请求身份始终匹配；重复请求不增加模型调用或重复统计用量。
6. 新一轮失败后输入建议、上一次成功摘要与候选全部保留。
7. 历史候选正常读取与采用，历史种子补充故事发动机时清楚标识原值缺失。
8. 正式种子只在显式采用后改变，运行互斥、过期候选拒绝、下游失效和采用后待确认行为保持有效。
9. 在 1280px 与 1440px 桌面宽度下，摘要清晰可读，长原文可展开，操作可用键盘完成。

## 9. 建议实施顺序

1. 先补共享 schema、固定路径和中文标签映射，测试路径约束与历史响应兼容。
2. 实现纯函数形式的字段比对，覆盖字符串、数组顺序、历史缺失和零变化。
3. 增加摘要存储字段及迁移，保留原候选 JSON 结构。
4. 新增提示词 v2、接入一次结构化生成、服务端说明过滤和原子存储。
5. 前端增加摘要与前后原文展开区，继续以整份成功预览为状态单元。
6. 补后端单测、HTTP 响应与去重测试、前端失败保留及展开交互测试，最后做桌面页面验收。

优先交付「改了哪些字段 + 简短说明 + 可展开原文」。逐字高亮、按字段选择采用和完整历史比较留待后续需求明确后再设计。

## 10. 实施补充

已按上述设计接入真实字段比对、v2 单次模型输出、独立摘要存储和前端前后原文展开。损坏摘要的 API 响应额外带可选 `changeSummaryWarning`，以区分历史无摘要与当前摘要不可用。历史响应的缺失摘要归一化为 null。
