# Rill 面向公众的长期上线改造计划

日期：2026-10-25  
状态：规划草案，逐块讨论后确定技术选型；尚未开始实现。  
目标：开放注册，让不同作者安全地独立创作，控制 AI 成本，并能持续发布、备份和恢复。

## 1. 已确认的范围

- 第一阶段直接面向公众注册使用，不以个人远程版作为公开上线交付目标。
- 当前没有服务器和域名，先比较部署路线，再采购资源。
- 保留 NestJS、React、TypeScript、Prisma 和现有 AI 基建；对需要变化的部分逐项评估。
- 保留历史作品、正文、审核、候选稿、导出和流水线进度；迁移必须有校验和恢复方案。
- 本文仅规划改造，技术建议不代表已批准实施或采购。

尚未确定：主要用户地区、月度基础设施预算、AI 费用承担方式、注册验证方式、收费方式、预计并发和可接受的数据损失时间。

## 2. 当前实现与主要差距

本节依据当前工作区代码检查，不代表已通过生产环境验收。

| 模块 | 当前实现 | 面向公众需要补齐 |
| --- | --- | --- |
| 身份与权限 | 未发现用户、会话和作品所有者模型 | 注册登录、会话撤销、作品归属、全链路权限验证 |
| 模型密钥 | 网页可以修改后端共享密钥，写入 `backend/.env` | 管理员权限、生产密钥存储和轮换；普通用户不可修改服务密钥 |
| 数据 | 业务 SQLite、独立 checkpoint SQLite、正文与导出文件 | 用户隔离、一致性备份、迁移和多进程访问方案 |
| 生成执行 | API 进程内执行，已有数据库条件更新防重与 checkpoint | 持久任务、租约、心跳、幂等、全局并发与公平调度 |
| 重启恢复 | 启动时统一清理运行状态；导出也有启动恢复逻辑 | 按执行者和租约恢复，不能在新实例启动时清理其他活跃实例任务 |
| AI 费用 | 已有 token 记录和单请求模型调用预算 | 用户级额度、预留与结算、全局费用上限、异常熔断 |
| 部署 | 已有 build/start；未发现生产容器、代理和 CI 配置 | 可重复构建、HTTPS、健康检查、自动发布、备份和回滚 |
| 健康检查 | `/api/health` 返回状态与时间戳 | 区分进程存活与依赖就绪，检查数据库、队列、存储 |

主要检查入口：`backend/src/main.ts`、`backend/prisma/schema.prisma`、`backend/src/llm/llm.controller.ts`、`backend/src/ai/key-settings.service.ts`、`backend/src/novel/pipeline/pipeline.service.ts`、`backend/src/novel/pipeline/project-run.ts`、`backend/src/novel/prose/prose-files.service.ts`、`backend/src/novel/book-export/book-export.service.ts`。

## 3. 分阶段路线与发布门槛

阶段按依赖推进，不承诺未经估算的日历日期。完成各模块方案讨论后，再拆分实施批次与估算。

| 阶段 | 交付目标 | 主要工作 | 验收门槛 |
| --- | --- | --- | --- |
| P0：确定产品与架构边界 | 形成可实施方案 | 用户地区、预算、收费与额度、部署路线、数据存储、登录方案、恢复指标 | 关键决策有记录，公开版范围与费用上限明确 |
| P1：安全与数据基础 | 支持独立用户与作品 | 账号、会话、权限、密钥权限、数据库迁移、历史数据归属、存储抽象 | 两个用户之间读写、下载和任务操作均不可越权；历史作品可验证恢复 |
| P2：可靠执行与成本控制 | 能承接多用户 AI 任务 | 队列、worker、租约、幂等、额度账本、限流、取消、超时、任务状态 | 重复提交、进程退出、超时重试不会重复应用结果；额度并发扣减正确 |
| P3：生产运行与受控验证 | 在真实环境验证完整链路 | 容器、域名、HTTPS、预发布、CI/CD、监控、备份、运营后台、故障演练 | 关键用户流程、负载和恢复演练通过，发布可回退，有费用和故障告警 |
| P4：公开注册上线 | 开放可控规模的公众注册 | 注册验证、防滥用、公开说明、容量限制、支持与反馈 | P1–P3 门槛通过；管理员可暂停注册、生成和新增消费 |
| P5：持续运营与扩容 | 根据实测增长 | worker 扩容、数据库优化、存储治理、模型评测、按需收费和高可用 | 每次扩容有指标依据，故障与成本可追踪 |

P3 的受控测试用于验证公众版，不省略账号、隔离和额度等公开上线要求。公开注册初期仍应设置总人数、总任务数和总费用上限。

## 4. 逐块技术方案与选型议题

### 4.1 部署地区、资源与网络

| 路线 | 适用条件 | 主要代价 |
| --- | --- | --- |
| 自管云服务器 + Docker Compose | 希望控制预算和环境，并能维护服务器 | 自行处理系统更新、备份、网络、证书、容量和故障 |
| 托管应用平台 + 托管数据库/对象存储 | 希望减少主机维护，接受平台费用与约束 | 需验证长任务、后台 worker、网络、日志、发布和存储限制 |
| 混合方案 | 应用自管，数据库和对象存储托管 | 需管理跨服务权限、网络和流量成本 |

建议优先比较自管与混合路线；先确定用户地区和预算，再比较具体服务商。应用与 worker 可以先放在同一台主机，但必须明确这是单机故障域，不能称为高可用。

待决定：用户主要在哪里、基础设施与 AI 的独立预算、是否愿意运维、域名、数据所在地，以及当地公开服务的备案、隐私和内容治理要求。涉及地区要求时另查官方资料，不在本草案中预判。

验收：目标地区访问、注册邮件、模型接口、文件上传下载均可达；费用包含数据库、磁盘、备份、日志和出网流量。

### 4.2 账号、登录与权限

候选：自建账号与服务端会话，或托管身份服务。对于当前同源 Web，优先讨论 HttpOnly、Secure Cookie + 服务端会话；需同时设计 CSRF 防护、过期、注销和会话撤销。接入外部身份服务也仍需应用自己的资源权限校验。

建议第一版只支持个人作品所有权和管理员角色，团队协作后续独立设计。权限由服务端身份推导，不能相信客户端提交的 userId。

任务：用户与会话模型；注册验证；登录限流；密码重置或身份服务回调；项目及其章节、候选稿、导出、回收站、任务的归属校验；管理员审计。若自行管理密码，使用成熟密码哈希库并单独评审参数与恢复流程。

验收：用户 A 无法通过猜测 ID、修改请求、导出链接或任务 ID 访问用户 B；注销和封禁能撤销会话；普通用户不能修改平台密钥。

### 4.3 业务数据库与历史迁移

候选：继续 SQLite 单机运行，或迁移 PostgreSQL。面向公众且准备拆分 API/worker，建议重点评估 PostgreSQL；不以“注册用户数”作为唯一迁移依据，要看并发写入、故障恢复和运维能力。

任务：确认 Prisma 适配器和生成流程；增加用户归属与额度账本；新建目标数据库迁移基线；编写数据搬迁、主键和关系校验、JSON 校验、计数与抽样比对；安排切换停写窗口。SQLite SQL 迁移不能直接当作 PostgreSQL 迁移使用。

历史无主作品：先列清单，明确归属到哪个管理员账号，审核后迁移，不直接归给首位公开注册用户。

checkpoint 是另一套状态存储，需独立选择兼容的 saver，并验证版本和恢复行为；换业务数据库不会自动迁移 checkpoint。

验收：迁移演练保留作品、正文与接受证据；迁移前可恢复备份；切换后写入有明确保护策略。数据库结构回退与应用版本回退分别评估。

### 4.4 正文、候选稿与导出存储

候选：持久本地磁盘，或私有对象存储。现有 `ProseFilesService` 使用文件哈希、原子替换和硬链接，不能机械替换为对象存储 API。

建议先定义存储接口和原子性语义，再选实现。若首版保留本地磁盘，所有写入进程必须共享同一权威存储，且限制扩容拓扑；扩容到跨主机前完成存储改造。

对象存储方案需设计不可变版本对象、数据库中的当前版本指针、条件更新、校验哈希、孤儿对象清理和私有下载授权。正文内容与元数据写入失败时必须可恢复。

验收：重建容器和服务重启不丢稿；陈旧候选不能覆盖新稿；未授权下载失败；备份恢复后版本、哈希与数据库引用一致。

### 4.5 后台任务与流水线恢复

候选：数据库持久任务 + worker，或 Redis + BullMQ。前者减少基础服务但需自行实现调度语义；后者有成熟队列能力但增加 Redis 运维。

建议将任务调度与 LangGraph 的工作流进度分开：队列负责何时执行，业务库负责任务和产物状态，checkpoint 负责工作流恢复位置。避免三处都作为同一状态的权威来源。

任务：任务 ID 和幂等键；数据库写入与入队的一致性（如 outbox）；租约、心跳、过期接管；每项目互斥；用户级和全局并发；重试退避；取消；停机排空；失败任务处理。保留现有数据库防重条件更新，并审查分布式执行时的完整性。

必须先改启动清理逻辑：API/worker 启动不能统一释放其他活跃执行者的状态。任务接管须验证租约及执行代次，阻止失去执行权的旧 worker 提交结果。

队列按可能重复投递设计。结果落库幂等不等于模型请求只计费一次；外部调用与本地提交之间的故障需要单独记录和对账，不承诺 exactly-once 模型调用。

验收：重复提交、worker 被杀、Redis/数据库短暂不可用、旧 worker 延迟返回、新实例启动均不破坏作品；页面能显示等待、执行、失败和重试状态。

### 4.6 AI 密钥、额度与费用

首先决定商业模式：平台承担模型费、用户自带密钥，或两者并存。这个决策影响额度、密钥存储、支持成本与支付需求。

平台密钥：只允许管理员配置；从生产 secret 配置读取；轮换有审计；不依赖网页写发布目录 `.env`。用户自带密钥：需独立的加密存储、主密钥管理和删除流程，禁止回显和写日志。

建议设计独立用量账本，包含用户、任务、调用、模型、用途、token、计价版本、状态及关联 traceId。现有项目累计 token 保留为展示数据，不能独立承担余额账本。

任务：注册赠送额度；调用前原子预留；最终结算或释放；超时和未知用量对账；每用户并发与日限额；全站硬上限；模型服务异常熔断。费用估算与供应商实际账单分开，价格配置版本化。

验收：并发请求不能透支；重试不会重复结算同一记账项；未知调用不会被直接视为零费用；管理员可停止新增消费，用户能理解额度不足原因。

### 4.7 Web 与 API 的生产行为

任务：同源 HTTPS；SPA 路由回退；保留 `/api` 路径的反向代理；Host 与代理信任范围；收紧 CORS；安全响应头；请求体上限；分层限流；通用错误响应；静态资源缓存和版本更新策略。

长任务优先立即返回任务 ID，通过轮询或后续 SSE 获取进度；仅对确实同步的操作调整代理超时。当前已有后台执行和轮询能力，先盘点接口，避免重复改造。

验收：页面深链接刷新正常；鉴权失败有明确反馈；部署后静态资源可加载；代理设置兼容密钥管理的来源检查；后台生成不依赖浏览器持续连接。

### 4.8 构建、环境与发布

建议采用可重复的容器构建，运行 Node 24；本地、预发布和生产各自独立配置、数据库、密钥和存储。

任务：锁文件安装；shared → backend → frontend 构建；Prisma generate；正确打包运行依赖和 Prisma 客户端；处理依赖 `prisma/schema.prisma` 定位目录的代码；非 root 运行；就绪检查；显式、单次运行迁移；版本标签与发布记录。

流水线：格式检查、lint、测试、构建 → 预发布迁移与验收 → 生产备份与发布 → 健康和关键路径检查。现有 `prisma7.config.ts` 的选择方式应写入脚本并实际验证，不能假设 CLI 自动发现。

验收：干净环境可构建启动；测试不调用真实付费模型；生产 secret 不进入镜像、前端包或日志；发布失败可返回兼容的旧应用版本。

### 4.9 监控、告警与运营后台

先用结构化日志、错误收集和少量关键指标，规模增长后再增加完整指标平台，避免初期监控费用失控。

观察：注册与登录异常、API 错误和延迟、队列等待与任务成功率、模型超时、token 与费用、额度对账差异、数据库连接、磁盘/对象容量、备份新鲜度。

后台最小能力：用户封禁、额度调整审计、失败任务定位、用量查看、暂停注册/生成、服务状态；作品正文的管理员访问要有明确权限与审计。

验收：能从用户报错关联到任务与模型调用；告警不包含密钥与完整正文；费用、备份失败和容量告警实际演练可到达负责人。

### 4.10 备份、恢复与容量

待协商恢复指标：RPO 表示最多可接受丢失多久的数据；RTO 表示故障后多久恢复服务。先确定指标，再选择备份频率与托管等级。

任务：业务库、checkpoint、正文/候选/导出、必要配置与密钥恢复材料；加密异地备份；保留周期；恢复演练。低流量阶段可以停写后做跨存储一致性快照；在线备份须明确数据库、正文版本和 checkpoint 的一致性边界。

若允许 checkpoint 丢失后从业务数据重建，须先验证各阶段恢复契约；不能仅凭历史兼容代码推断全部阶段都可重建。备份不能简单复制仍在写入的 SQLite 主文件并假定完整。

验收：从空环境恢复选定时间点，核对稿件哈希、项目阶段、候选稿、下载和账本；记录实际恢复时间。

### 4.11 公开服务、隐私与防滥用

地区和服务范围确定后，专项确认隐私说明、用户协议、作品权利、第三方模型数据传输、数据导出与删除、内容投诉和适用的公开服务要求。

任务：注册验证与速率限制；异常账号和批量消费识别；敏感操作审计；用户删除及备份过期策略；管理员联系渠道。验证码、内容处理服务等按实际风险与地区选择，避免将 IP 作为唯一封禁依据。

验收：用户知道作品如何存储、哪些内容发给模型、如何导出和删除；滥用时能停止新增消费；所有公开注册路径受同一额度规则约束。

### 4.12 商业化与后续扩容

如果公开上线即收费，支付、订单、退款说明和权益账本提升为 P4 前置；如果免费且有硬额度，可以后续再做支付。

支付必须验证签名、处理重复通知、对账，并让订单与 AI 额度结算保持可追踪。具体支付渠道待用户地区和主体条件确定。

扩容触发依据：任务等待时间、并发写压力、worker 资源、模型供应商限流、存储增长、故障恢复目标。先解决瓶颈，再决定增加 worker、托管数据库、CDN 或高可用；不预设 Kubernetes 为必要目标。

## 5. 依赖与实施顺序

1. 确认地区、预算、AI 费用承担方式和首版开放规模。
2. 确认目标架构、恢复指标、登录与数据库选型。
3. 建立权限、用户归属、生产配置与历史数据迁移基础。
4. 明确存储一致性与任务状态权威，完成 worker、租约和恢复改造。
5. 接入额度账本、限流和费用控制，避免公开注册后无上限消费。
6. 在预发布整体验证发布、备份、恢复、越权和故障场景。
7. 完成公开说明、运营入口与容量边界，再开放注册。

账号权限与部署骨架可在契约确定后分批推进；存储改造和任务扩容需先达成一致性设计。每个模块交付都包含契约、迁移、实现、测试与文档。

- [ ] 监控、费用告警、备份告警、回滚手册和支持渠道可用。
- [ ] 根据部署地区完成适用要求确认与公开说明。
