# 正文按建议修改设计方案

日期：2026-10-25  
状态：核心流程已实施；真实模型质量样例待验收  
范围：移除正文工作台的手动修改与 AI 候选稿流程，新增统一的「按建议修改」模块。

## 1. 方案结论

作者在正文页面选择 AI 审核建议，或填写自己的修改建议。系统基于当前章原文生成修改结果，先展示实际改动，再由作者点击「应用修改」。系统直接更新正式正文，自动重新审核，通过后生成摘要，最后仍需人工接受本章。

```text
当前正文
  → 选择审核建议 / 填写修改建议
  → 生成修改预览
  → 查看本次改动与修改后全文
  → 应用修改
  → 自动 AI 审核
      → 通过：生成摘要 → 人工接受 → 继续后文
      → 未通过：留在本章，再次修改或填写理由保留正文
```

设计选择：保留一次应用前的预览，避免建议理解有误时直接覆盖原文。预览属于同一个修改模块，不再产生供用户管理的候选 Markdown、不展示候选路径、不需要本地合并，也不提供独立「重新生成一章」入口。

本方案已进入实施：统一修改入口、逐条建议选择、预览与应用、自动重审及恢复机制已接入。自动化验证使用模拟模型；真实模型对建议的理解与局部改写质量仍需样例验收。

## 2. 删除与保留的范围

| 项目                                                     | 处理                                                       |
| -------------------------------------------------------- | ---------------------------------------------------------- |
| 「刷新本地修改」按钮、本地编辑引导、复制路径作为编辑入口 | 移除                                                       |
| 「修改后刷新并重新审核」操作                             | 替换为「按建议修改」                                       |
| 「更多操作 → 生成候选稿」及候选稿列表                    | 移除                                                       |
| 旧 `/regenerate` 正文接口                                | 停止生成，返回明确的能力下线提示；不能暗中映射成新修改接口 |
| 正文阅读、首次生成、审核、摘要、逐章人工接受             | 保留                                                       |
| 「填写理由，保留当前正文」                               | 保留，用于作者不同意审核意见的情况                         |
| 本地 Markdown 正式文件                                   | 保留为现有正文存储格式，由后端负责受控更新                 |
| 文件扫描、哈希核验、版本校验                             | 保留为内部一致性机制，不再作为正常修改操作暴露             |
| 历史正文、旧候选文件、审核与接受记录                     | 保留数据；旧候选仅归档，不自动应用、不自动删除             |

移除手动修改指产品不再提供或依赖本地编辑工作流。已有磁盘文件仍可能被外部工具改变，后端必须继续检测并阻止覆盖冲突，不能因此移除安全检查。

本方案取代 `docs/prose-workbench-stepper-design.md` 中有关本地编辑、候选生成及合并的设计；旧文档的五步进度、顺序接受和审核放行规则继续适用。实施时同步更新该文档及当前能力规范，不修改已归档变更来追认新行为。

## 3. 模块入口与页面布局

沿用当前 Ant Design 工作台，在正文预览之后、AI 审核报告附近加入「按建议修改」卡片。已生成且文件有效的章节均可进入，包括已接受章节；无正文时只展示首次生成。

```text
第 4 章                         全书已接受 3 / 12 章
生成正文 → AI 审核 → 生成摘要 → 人工接受 → 已接受

正文内容……

AI 审核 · 建议润色
问题、原文依据、修改建议……
[按建议修改]  [填写理由，保留当前正文]

按建议修改
采用哪些审核建议（可多选，默认不勾选）
已选 2 / 3 条                         [全选] [清空选择]
☑ 建议 1 · 加强结尾行动与下一章的联系
☑ 建议 2 · 缩短中段重复解释
☐ 建议 3 · 增加人物正面冲突

补充修改建议（可独立填写）
[让主角的犹豫通过动作表现，减少心理独白。       ]
仅修改本章，保留未涉及的情节与人物设定。
[生成修改预览]

本次修改 · 3 处
本次采用：建议 1、建议 2；补充要求：通过动作表现犹豫。
• 中段：删除重复解释（可展开修改前后）
• ……
[查看修改后全文]
[应用修改并重新审核]  [放弃本次修改]
```

交互规则：

- 审核未通过时，进度区主操作「按建议修改」定位到卡片，并聚焦建议区域。其他状态使用次操作展开卡片，原有接受主操作保留。
- 审核建议不是强制项；至少选择一条当前报告的建议，或输入一条非空建议，才可生成。
- 补充建议最多 2000 个字符；标签、字数和校验信息可见，不能只用 placeholder 说明。
- 审核项以报告 ID 与条目索引定位，后端从该报告读取真实建议，不信任客户端传回的建议正文。
- 已失效或缺失的报告不能作为建议来源，但前文及大纲有效时仍可填写自己的建议。
- 用户可直接填写「重写本章，保留结局，强化冲突」，无需额外提供无建议的整章重生按钮。
- 预览必须先显示可读改动，再显示全文；差异由后端对比原文和新文生成，不能将模型自述当成实际变化。
- 同时最多一份可应用预览。修改建议后重新生成，须明确新的成功结果将替换旧预览；失败保留上次预览及其原始建议，不能混淆两者。
- 「放弃」只取消未应用修改。首版不增加历史版本管理、逐处采用、预览上的连续修改或应用后的撤销入口。
- 切换章节后，服务端预览可恢复；输入草稿按项目和章号隔离，不能带到其他章节。
- 生成、应用、重新审核分别显示准确状态；仅有生成在运行时，不让正文五步条倒退到「生成正文」。

窄屏使用上下排列的修改前后片段，保留换行与段落；不强制双栏或横向滚动。复用现有主题，不引入新设计系统。按钮提供明确文字、键盘焦点、至少 44px 触控区域；加载使用 `aria-busy`，错误显示在模块内并保留输入。

### 3.1 逐条选择 AI 审核建议

「接受某条建议」在本模块中表示将它纳入本次修改要求，勾选本身不会改正文、放行审核或接受本章。统一使用「选择建议」和「应用修改」文案，避免与流水线的「人工接受」混淆。

| 项目         | 规则                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------------- |
| 选择粒度     | 每条审核 issue 对应一项独立复选框，可选一条或多条；一条 issue 内的多句建议首版作为整体选择                           |
| 展示内容     | 每项展示序号、问题、严重程度和建议；原文证据、位置及依据可展开查看                                                   |
| 默认值       | 默认全部不选，包含 critical 的建议也不自动选择                                                                       |
| 批量操作     | 提供「全选」「清空选择」，显示已选数量；全选须由作者主动触发                                                         |
| 提交范围     | 只把勾选项与作者补充建议作为本次修改要求，未勾选项不发送为待执行建议                                                 |
| 无勾选       | 允许仅填写自己的建议；两者均为空时禁用生成并显示原因                                                                 |
| 所选建议冲突 | 所选项之间或与补充要求冲突时，返回具体原因，要求作者调整，不让模型自行选择执行哪一项                                 |
| 选择发生变化 | 旧预览仍绑定生成时的建议快照；显示「建议已变化，请重新生成预览」，禁用旧预览的应用按钮，恢复原选择及输入后可重新匹配 |
| 报告更新     | 清除旧报告的勾选，提示重新选择；不能按同一索引自动勾选新报告中的不同问题                                             |

例如报告提出「压缩心理描写」「加强结尾悬念」「增加人物冲突」，作者只选择前两条，则此次不要求 AI 增加人物冲突。执行所选建议所必需的衔接调整允许发生，但必须呈现在真实差异中；不得借机处理所有未选问题。

预览顶部固定展示本次所选建议及补充要求，逐项列出「AI 处理说明」，作者可结合下面的实际修改片段核对。该说明是模型自述，不能标成已被程序验证的「已解决」。正式重新审核仍检查完整正文，未选问题可以再次出现在新报告中；不因本次没有选择就视为解决或自动放行。

## 4. 正文修改规则与模型输入

新增注册提示词 `prose-revision/v1`，走现有模型注册、LLM 调用、错误分类和用量记录。

输入包括：当前章完整原文、所选审核问题与证据、作者补充建议、已确认问卷、世界观与人物、本章大纲、前文有效摘要及当前文风约束。优先复用当前正文依赖组装逻辑，前文摘要的选择策略应与生成/审核兼容。

模型必须：

1. 以当前原文为修改基础，针对建议调整；保留无关内容，不默认重写全章。
2. 保留用户明确选择的类型、视角、篇幅和文风，禁止改动上游设定或其他章节。
3. 建议与已确认大纲、人物等约束冲突时，返回具体冲突原因，提示先修改上游；不能静默改设定。
4. 输出结构化结果：`outcome: revised | blocked`、完整 `content`、`explanation`，成功结果增加 `suggestionResponses: [{ issueIndex, explanation }]`，逐条解释所选审核建议的处理方式。后端校验索引集合与所选集合完全一致，不能缺项、重复或包含未选项；没有勾选时返回空数组。成功时正文非空，冲突时仅提供原因；通过 Zod 联合类型限制合法组合。
5. 拒绝截断、空输出和格式异常；保留正常 Markdown，不添加模型解释到正文中。
6. 只执行所选建议及补充要求；不得将整个审核报告作为待执行清单。未选项不会被标为已处理，局部修改不得扩大为无关重写。所选项之间、与补充要求或上游约束冲突时返回 blocked，不静默取舍。

输出全文便于可靠替换；首版不采用模型提供的行号补丁，避免原文定位错误。后端统一换行，执行段落/行差异计算，得到新增、删除和替换片段。字符统计明确写为字符数，不冒充汉字数。无实际变化时返回 `unchanged`，不提供应用按钮、不递增正文版本。

模型提供的 explanation 只作补充说明。展示真实差异是确定性能力；建议是否被充分落实属于模型质量，需通过样例验收和作者预览判断，不承诺程序能证明所有建议已满足。

## 5. 状态与生效时机

修改记录状态：

```text
generating → ready → applying → applied
     ├→ blocked / unchanged / failed
ready → discarded / stale
applying → conflict / recovery_required
```

| 操作                       | 正式正文           | 审核、摘要与后续章节                            |
| -------------------------- | ------------------ | ----------------------------------------------- |
| 填建议、生成预览、放弃预览 | 不变               | 不变                                            |
| 成功应用修改               | 替换为修改后的全文 | 本章重新审核；本章及后文章节原接受/摘要依赖失效 |
| 应用后审核未通过           | 保留已应用正文     | 停在审核节点，等待再次修改或作者放行            |
| 应用后审核/摘要执行失败    | 保留已应用正文     | 重试对应机器步骤，不重新修改或重复应用          |
| 再次人工接受               | 不再改正文         | 使用新摘要继续后文复核或生成                    |

允许修改历史已接受章节，但须保证该章之前的正文和摘要均有效、大纲已确认。卡片预先显示影响：「应用后，第 N 章起需要重新审核确认，后文章节原文将保留」。不能复用只允许最早待处理章的生成门禁来禁止历史章修订；应新增修订专用门禁，人工接受仍严格按顺序。

应用修改只触发本章审核和摘要，不自动接受、不自动续写下一章。后文已存在正文时按现有规则复核，不因前文变化自动覆盖。全书已完成时清除完成标记并回到正文阶段。

已有导出文件及快照保留其原有内容，沿用快照指纹标识其与当前正文是否一致；新导出继续要求正文满足当前交付门禁。

## 6. 共享契约与 API 草案

先在 `shared/src/index.ts` 定义 Zod schema 和类型，再实现前后端。以下路径相对于现有 `/api/novel/projects/:id/prose/chapters/:number`：

| 方法与路径                            | 请求要点                                                                                                     | 行为                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| `POST /revisions`                     | `requestId`、`expectedRevision`、`expectedHash`、`feedback?`、`reviewSelection?: { reviewId, issueIndexes }` | 持久化任务，返回 `202` 与 revisionId，后台生成修改预览       |
| `GET /revisions/:revisionId`          | 无                                                                                                           | 读取生成状态、建议快照、预览、实际差异、失败原因及可应用状态 |
| `POST /revisions/:revisionId/apply`   | `requestId`、`expectedRevision`、`expectedHash`                                                              | 短操作应用正文并登记后续审核任务，返回可恢复的应用状态       |
| `POST /revisions/:revisionId/discard` | 无                                                                                                           | 放弃 ready 记录，重复调用幂等                                |

正文详情增加 `activeRevision` 摘要，包括 ID、状态和基础版本，页面重载后可找到进行中的任务。轮询只针对当前记录；章节切换后按 revisionId 归属更新，避免旧响应覆盖新章节。

请求约束：版本字段复用现有 schema；feedback 去空白后限长；选项索引去重、限制在报告范围内；至少有一种有效建议来源。后端验证报告属于当前项目/章号，且绑定当前原文与依赖。正文有效性、项目未删除、前文及大纲有效、运行互斥均由服务端最终判断。

创建任务时由服务端捕获 `dependencyFingerprint`。生成完成和应用前均复核原文版本、哈希、依赖指纹；变化时标记 stale/conflict，不能自动套用到新原文。相同 requestId 与相同请求返回原记录，重复 ID 配不同内容返回冲突；同章相同正文与建议已有成功预览时可直接返回已有结果，避免无意重复计费。

生成和应用复用现有项目运行互斥；待确认预览不长时间占用运行锁。现有流水线若只支持等待整段请求结束，需要扩展持久任务领取/恢复机制，不能仅在控制器使用无追踪的异步 Promise。新增活动状态明确目标章号、revisionId、操作阶段与错误，页面重载后仍可追踪。

## 7. 数据、文件写入与异常恢复

建议新增 `ProseRevision`，不将具有完整状态的新修订流程硬塞进旧候选操作字段。主要字段：

| 分类       | 字段                                                                         |
| ---------- | ---------------------------------------------------------------------------- |
| 归属与幂等 | id、projectId、chapterNumber、requestId、requestHash                         |
| 基础快照   | baseRevision、baseHash、dependencyFingerprint、originalContent               |
| 用户输入   | feedback、reviewSelectionData、resolvedSuggestionsData                       |
| 修改结果   | content、resultHash、changeSummaryData、explanation、suggestionResponsesData |
| 执行状态   | status、errorCode、errorMessage、createdAt、updatedAt、appliedAt             |

JSON 数据使用 String 持久化，读写经共享 schema 校验。项目删除级联处理；纳入现有软删除/运行中删除门禁与恢复流程。用量复用现有 trace 去重记录，区分 `revision`、`review`、`summary` 用途并进入现有项目用量统计；失败调用的已发生用量同样记录。

当前 `ProseFilesService` 仅支持安全创建，不能直接拿创建方法覆盖已有章节。新增受控替换能力：

1. 取得项目写锁并重新读取正式文件、数据库版本和依赖，核对基线。
2. 将原文快照、目标结果及 apply 操作日志持久化，记录目标哈希；生成同目录临时文件并同步写入。
3. 在不允许后台扫描并发介入的发布临界区，再次核对目标与基线，使用原子 rename 发布新文件。
4. 在数据库事务中更新 observedHash/fileStatus、修订应用状态，并使本章及后文旧审核、摘要、接受依赖失效。避免同次应用被 reconcile 再次算作一次修改。
5. 持久登记重新审核任务，再释放锁；机器步骤失败与「正文是否应用」分开记录。

数据库事务与文件系统不是同一事务，必须使用日志恢复，不能写成「一个事务原子完成」。启动及任务恢复时检查未完成操作：

- 文件仍是基础哈希：可从已持久结果重试发布。
- 文件已是目标哈希：幂等补齐数据库失效和任务登记，不重复递增版本。
- 文件既不是基础也不是目标哈希：进入 conflict，保留所有快照，不覆盖未知内容。

扫描和任务领取在恢复完成前不得放行人工接受或新导出。保留现有路径越界和符号链接检查。项目锁只能约束应用内写入，普通文件系统不提供对任意外部编辑器的哈希 CAS；发布前后校验可发现大部分外部变化，但不能承诺与所有外部写入完全互斥。产品退出本地编辑流程后，以应用独占管理输出文件为正常使用前提，外部变化按异常处理。

## 8. 失败与反馈

| 情况                     | 用户看到的结果                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| 未选择建议且输入为空     | 就近提示填写或选择建议，不发请求                                                                 |
| 模型失败/截断/不合法输出 | 原文保留，输入保留，可重试；旧成功预览继续可查                                                   |
| 与上游设定冲突           | 显示具体冲突，提供前往对应阶段的导航，不显示应用按钮                                             |
| 结果未发生变化           | 显示「未检测到正文变化，请补充更具体的建议」                                                     |
| 预览生成后原文或依赖变化 | 显示「正文或前文已变化，请重新生成修改预览」                                                     |
| 应用成功，审核失败       | 明确显示「修改已应用，AI 审核失败」，主操作为重试审核                                            |
| 请求超时或页面关闭       | 重载从记录查到真实结果，不能凭请求失败断言未应用                                                 |
| 磁盘写入失败或恢复冲突   | 显示恢复状态，暂停进一步写入；不引导用户再次生成来覆盖原文                                       |
| 文件丢失/损坏            | 有可信已应用快照时提供独立的「恢复已保存正文」操作；没有可信快照则明确报错，不能拿新生成冒充恢复 |

## 10. 验收标准

- [ ] 正文页面没有本地编辑、刷新本地修改、候选稿生成、候选路径或本地合并入口。
- [ ] 作者只填自己的建议、只选审核建议、同时使用两者，均可发起修改；空建议不能提交。
- [ ] 每条审核建议独立可选、默认不选；全选与清空准确更新数量，严重问题不被自动勾选。
- [ ] 只选三条中的两条时，模型执行输入仅含这两条与补充要求；预览展示其建议快照和逐项处理说明，不将未选建议视为已解决。
- [ ] 所选建议之间或与补充要求冲突时明确阻塞；改变选择或输入后不能直接应用不匹配的旧预览。
- [ ] 报告更新后旧勾选失效，不按旧索引误选新问题；重新审核仍能报告未处理的问题。
- [ ] 生成以当前章原文为基础，保持明确的创作约束，不改其他章节。
- [ ] 先显示实际修改片段，再提供修改后全文；无改动、冲突、非法输出不能应用。
- [ ] 预览和放弃不影响正式正文、历史接受或后文状态。
- [ ] 点击应用后无需任何本地文件操作；更新正式正文、重新审核并在通过后生成摘要。
- [ ] 修订不会自动接受本章；审核不通过时可再次修改或填写理由保留。
- [ ] 已接受历史章可修改，影响范围可见；下游正文保留、依赖失效，顺序复核继续成立。
- [ ] 生成/应用防重复；断网、重载、重复请求不重复覆盖、不重复应用、不重复统计用量。
- [ ] 原文、报告或依赖变化会使预览失效；不能跨项目、跨章节或用旧报告应用修改。
- [ ] 覆盖前、rename 后、数据库提交前后等故障点均能恢复到可解释的一致状态，接受与导出不会读取半完成状态。
- [ ] 审核或摘要失败时只重试缺失步骤，页面清楚区分修改失败和应用后的审核失败。
- [ ] 旧项目正文不丢失，旧候选不被删除或自动采用，旧接口不能继续生成候选。
- [ ] 桌面和窄屏下建议、差异、按钮可读可操作，键盘及读屏可感知运行与错误状态。
