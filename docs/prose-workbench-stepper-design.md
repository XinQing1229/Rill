# 章节正文工作台：步骤条与操作按钮设计

日期：2026-10-23  
状态：部分规则已由后续方案替代  
范围：正文工作台的单章步骤展示、按钮组织、异常恢复与章节切换。

本文为独立设计文档，不创建 OpenSpec 变更。本次只产出设计，不修改应用代码。

> 2026-10-25 更新：本地编辑、刷新本地修改、候选生成和合并已由 [正文按建议修改设计](./prose-feedback-revision-design.md) 取代，不作为当前实施要求。

## 1. 设计目标

让作者进入正文工作台后能直接回答三个问题：本章进行到哪一步、为什么停住、下一步点击什么。

采用固定的五节点步骤条：

```text
生成正文 → AI 审核 → 生成摘要 → 人工接受 → 已接受
```

前四个节点代表工作步骤，「已接受」代表终态。正常生成时，前三步自动连续执行；人工接受完成后继续下一章。步骤条不是要求作者逐项点击的向导。

设计原则：

- 每个章节操作区最多显示一个主按钮，文案直接说明当前动作。
- 步骤、阻塞原因与操作放在一起；正文、报告、摘要仍可同时查阅。
- AI 审核通过与作者接受是两个不同状态。
- 自动模式同样保留每章人工接受。
- 保留本地 Markdown 编辑、文件校验、顺序接受、版本校验和候选稿机制。

## 2. 当前页面问题

当前 `ProseWorkbench` 用单个 Tag 显示 `machineStep`，按钮则分散在顶部和正文下方：

- 「生成 / 继续机器步骤」没有说明当前将生成正文、审核还是摘要。
- 「审核 / 摘要重试」合并了两个不同的恢复动作。
- 「生成候选稿」与最终接受并列，容易被理解为正常流程的必经步骤。
- 「接受正文与摘要，继续」未明确接下来生成新章、复核旧章还是结束全书。
- 多个禁用按钮同时出现，作者需要自行推断不可用原因。

另一个需要修正的展示细节：当前后端在已有有效报告但没有摘要时返回 `machineStep=summary`，即使报告结论为 `polish/rewrite` 且尚未放行。此时页面应定位在「AI 审核 · 待处理」，不能暗示审核已通过。

## 3. 页面布局

桌面端示意：

```text
正文                                  全书已接受 3 / 12 章
章节 [第 4 章 · 待人工接受 ▾]           [返回当前待处理章节]

✓ 生成正文 ─ ✓ AI 审核 ─ ✓ 生成摘要 ─ ④ 人工接受 ─ ⑤ 已接受

等待你接受第 4 章
请检查当前正文、AI 审核报告和摘要。接受后将生成第 5 章。
[接受本章并生成下一章]    [刷新本地修改]    [更多操作 ▾]

章节文件路径 [复制]
正文预览

AI 审核报告 · 通过 / 建议润色 / 建议重写
七维评分、问题、正文引用、依据、建议

待接受摘要
关键事件 / 人物变化 / 伏笔线索 / 连贯性说明

候选稿（存在时显示，可展开）
```

布局规则：

1. 章节选择器之下显示所选章节的步骤条，不能混用其他章节的进度。
2. 步骤条下面统一放置状态说明、异常信息、主操作与辅助操作，移除原顶部的笼统生成按钮和正文下重复操作区。
3. 主操作区保持在普通文档流中，避免浮层遮挡正文。长篇阅读结束处提供「返回本章操作区」锚点，不复制第二组业务按钮。
4. 路径保留复制能力；本地编辑提示缩为辅助说明，文件异常时提升为明确告警。
5. AI 报告与摘要默认展开，已有候选稿使用折叠区域。
6. 页面顶部通用「确认并推进」在正文阶段隐藏，正文只使用逐章接受入口。

## 4. 步骤条状态规则

### 4.1 基础映射

| 业务状态                     | 当前节点 | 已完成节点        | 提示                         |
| ---------------------------- | -------- | ----------------- | ---------------------------- |
| 正文尚未生成                 | 生成正文 | 无                | 准备生成本章                 |
| 正文有效，无有效审核报告     | AI 审核  | 生成正文          | 等待审核或审核失败待重试     |
| 报告建议润色/重写，未放行    | AI 审核  | 生成正文          | 需要处理审核意见             |
| 报告通过或已放行，无有效摘要 | 生成摘要 | 生成正文、AI 审核 | 等待生成摘要或摘要失败待重试 |
| 正文、报告、摘要均有效       | 人工接受 | 前三步            | 等待作者检查并接受           |
| 本章接受有效                 | 已接受   | 前四步            | 已接受，可供后文使用         |

展示优先级：文件异常、依赖阻塞 → 未放行的审核意见 → 其余有效 `machineStep`。已接受判断必须以最新服务端有效状态为准，不能只检查历史接受记录。

### 4.2 节点视觉

- 已完成：勾选图标；当前可执行步骤：主题色与序号；后续步骤：中性色。
- 正在执行：只有确定正在运行的步骤才显示加载图标。
- 执行失败：对应节点显示错误图标与「失败」说明。
- 审核建议润色/重写：使用警告状态并写明「待处理」，与网络错误或模型执行失败区分。
- 放行后：审核节点完成，说明为「作者已放行」，报告仍保留原结论和理由。
- 已接受后的正文发生变化：回到 AI 审核；后文依赖变化时显示「需复核」，完成标记按服务端最新状态重新计算。
- 步骤条只展示状态，不允许点击跳步或触发模型调用。

### 4.3 实时状态的能力边界

当前 `machineStep` 主要表示下一项未完成工作，并不等于精确的正在执行步骤。`project.status=running` 也可能来自候选稿生成或其他章节操作。

本设计首版复用现有接口：

- 空闲时按最新产物确定节点与操作。
- 有明确本地操作上下文时，在操作按钮显示加载文案；通用流水线运行时显示「正在处理正文，请稍候」。
- 轮询发现报告或摘要产生后推进完成节点；不能仅凭 `running` 给所选章节节点添加运行动画。
- 页面重载后只恢复可确认的进度，不虚构具体运行步骤或百分比。

如果后续要求实时准确区分正文生成、审核、摘要、接受和候选生成，需要另行扩展共享契约，返回绑定章号、运行标识的活动信息。本设计不将该扩展作为首版前置条件。

## 5. 主按钮决策表

下表默认所选章是最早待处理章节，文件与依赖门禁满足，且项目没有正在执行的操作。

| 状态                               | 主按钮               | 行为                                         |
| ---------------------------------- | -------------------- | -------------------------------------------- |
| 首次生成，有资格创建正文           | 生成本章正文         | 启动正文生成，并自动继续审核和摘要           |
| 首次正文生成失败，尚无已落盘正文   | 重试生成正文         | 继续未完成生成，不覆盖已有文件               |
| 正文有效，尚未审核                 | 审核本章             | 运行审核，通过后自动生成摘要                 |
| 审核执行失败                       | 重试 AI 审核         | 重试审核，不重新生成正文                     |
| 审核建议润色或重写，未放行         | 修改后刷新并重新审核 | 先扫描本地文件；确认修改后再调用审核恢复动作 |
| 报告通过或已放行，摘要未生成       | 生成本章摘要         | 复用有效报告，生成摘要                       |
| 摘要执行失败                       | 重试生成摘要         | 仅补摘要，保留正文和有效报告                 |
| 待人工接受，后续是新章             | 接受本章并生成下一章 | 接受当前正文、报告和摘要，继续下一章机器步骤 |
| 待人工接受，后续已有正文需复核     | 接受本章并继续复核   | 接受当前章，继续处理最早待复核章，不覆盖原文 |
| 待人工接受，接受后全书满足完成条件 | 接受本章并完成全书   | 接受当前章，完成正文阶段                     |
| 所选章已接受，全书未完成           | 前往当前待处理章节   | 只切换所选章节，不发起模型调用               |
| 全书已接受                         | 无业务主按钮         | 显示「全书正文已接受」，保留查看与本地刷新   |

「修改后刷新并重新审核」的交互细节：

1. 提示作者在展示的文件路径中修改并保存正文。
2. 点击后先获取最新详情，并确认观察到新的正文哈希或依赖版本变化。
3. 正文变化且门禁允许时，使用最新详情发起重试。
4. 如果未检测到变化，提示「未检测到正文修改，请先保存本地文件；也可填写理由保留当前正文」，不重复发起模型请求。
5. 刷新或扫描失败时停止，显示错误，不继续审核。

主按钮决策需同时输出文案、动作、可用性与原因，不能仅根据标签字符串分散判断。后一章仍有未解决文件问题时，接受本章可以成功，但后续处理可能失败，反馈必须区分两者。

## 6. 辅助按钮与审核放行

### 6.1 固定辅助操作

- **刷新本地修改**：始终容易找到；只读取、扫描并同步最新状态，不调用模型。运行期间可禁用并显示「正在处理，请稍候」。
- **返回当前待处理章节**：查看历史章或未来章时显示；只切换章节。
- **复制路径**：文件路径旁的轻量操作。

### 6.2 更多操作

「生成候选稿」移入「更多操作」，仅在本章已有可读取正文且门禁允许时出现。菜单说明：「另存一份候选稿，采用时请在本地合并」。

候选稿生成中显示独立提示「正在生成候选稿，当前正文保留」，不能将原文步骤条重置为「生成正文」。完成后展开新候选稿及路径。文件合并后按正文修改规则重新审核、生成摘要并接受。

没有正文时只提供正常生成入口。候选文件缺失或不可读只影响该候选区域，不阻塞有效正文的接受。

### 6.3 审核未通过时的放行入口

报告卡片显示次操作 **「填写理由，保留当前正文」**，点击展开带可见标签的理由输入框。

- 提交按钮：**「保留原判并生成摘要」**；理由为空或只有空格时不可提交，旁边说明原因。
- 使用当前 `revision/hash/reviewId` 提交；成功后进入摘要步骤，不直接接受。
- 报告保留「建议润色/重写」及作者理由，不能改写为「AI 审核通过」。
- 执行失败或缺失的报告没有放行入口，必须先重试得到有效报告。

## 7. 阻塞、异常与章节切换

| 情况                                     | 展示与操作                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| 上游大纲未确认/失效                      | 在状态区写明阻塞原因；暂停生成和接受，保留查看、刷新与前往相应阶段的导航       |
| 前文待接受或需复核                       | 显示「请先处理第 N 章」，主按钮为「前往第 N 章」                               |
| 已有正文文件缺失、为空、编码错误、不可读 | 明确章号、路径及恢复建议；主按钮「重新检查文件」，不映射成重新生成，不静默覆盖 |
| 版本冲突                                 | 刷新最新详情，提示「正文或依赖已变化，请重新检查」，不自动重提接受或放行       |
| 接受成功，但下一章处理失败               | 显示「第 N 章已接受；第 N+1 章处理失败」，切换到失败章节提供对应重试           |
| 候选生成失败                             | 在候选操作区域提示，可重试候选生成；原文步骤与有效报告保持原状态               |
| 状态读取失败                             | 展示「状态暂时无法更新」与「重新加载」，禁用依赖旧版本的写操作                 |

首次进入：默认选择最早待处理章；全书完成时选择最后一章。首次尚无章节记录时展示第 1 章的待生成步骤条，目标章数尚未返回时显示「—」，不编造进度。

执行期间：允许阅读和切换章节，但写操作统一锁定；运行提示必须指明已知的目标章号，不能随选择器变化。轮询更新不强制切换用户正在阅读的章节。

用户主动接受本章后：服务端返回本章已接受且下一章成为待处理章时，切换到该章；若期间用户已手动选择别章，则保留选择并提示「第 N 章正在处理」。超时或请求中断时先刷新确认接受结果，再决定是否重试。

## 8. 视觉与可访问性

- 复用项目 Ant Design 主题，桌面使用小尺寸水平 Steps；窄屏改为垂直 Steps，按钮组换行，不产生横向滚动。
- 状态色使用语义 token，并配合图标和文字表达，不能只靠颜色区分。
- 主按钮始终排在操作组首位；更多操作降低视觉权重，放行使用次按钮。
- 按钮提供明确加载文案，例如「正在审核」「正在接受并继续」；前端立即防重复提交，后端仍负责幂等与并发校验。
- 禁用原因使用可见文字，不只放在悬浮提示内。
- 章节状态更新使用礼貌级别的读屏通知；执行失败在就近区域告警。
- 步骤容器提供可访问名称「第 N 章创作进度」，当前节点带 `aria-current=step`。
- 保留键盘焦点样式；触屏按钮点击区域至少 44px。系统减少动态效果时取消非必要动画。

## 9. 实施落点与接口复用

建议在现有正文目录中拆分展示和决策逻辑：

| 文件/组件                  | 职责                                             |
| -------------------------- | ------------------------------------------------ |
| `ProseWorkbench.tsx`       | 章节选择、请求协调、轮询与产物展示               |
| `ProseChapterSteps.tsx`    | 五节点步骤条与状态说明                           |
| `ProseChapterActions.tsx`  | 单一主操作、辅助操作、更多菜单                   |
| `prose-ui-state.ts`        | 统一计算步骤、业务阻塞、按钮、目标章节与反馈文案 |
| `ProseWorkbench.css`       | 操作区、步骤条、窄屏布局                         |
| `ProjectWorkspacePage.tsx` | 正文阶段隐藏通用阶段确认入口                     |

复用现有接口：

- 读取/刷新：`GET /api/novel/projects/:id/prose`。
- 首次启动/整体恢复：现有 `generateStage`。
- 单章审核、摘要恢复：`POST /api/novel/projects/:id/prose/chapters/:number/retry`，由服务端继续缺失步骤。
- 候选稿：同路径下的 `/regenerate`。
- 放行：同路径下的 `/override`，携带版本、报告 ID 与理由。
- 接受：同路径下的 `/confirm`，携带 `expectedRevision/expectedHash/reviewId/summaryId`。

首版以现有返回字段做保守展示，不新增持久化 UI 状态。状态在页面重载后必须能从服务端详情重新推导。服务端目前未结构化返回所有依赖阻塞，已知阻塞可先提示；未能预判的门禁以请求返回为准，失败后刷新并展示具体原因，不承诺按钮可点击即必然成功。

## 10. 验收场景

- [ ] 首次生成可看到五节点步骤条，主按钮明确写「生成本章正文」。
- [ ] 正常生成自动经过正文、审核、摘要，最终停在人工接受，不自动接受。
- [ ] 审核建议润色/重写时定位在 AI 审核，不能显示为已通过或待人工接受。
- [ ] 修改后可刷新并重新审核；未保存修改时给出提示且不重复调用模型。
- [ ] 放行必须填写非空理由，保留原判，生成摘要后仍需人工接受。
- [ ] 摘要失败只提供摘要重试主操作，不诱导重新生成正文。
- [ ] 待接受时按后续状态显示生成下一章、继续复核或完成全书的准确文案。
- [ ] 已接受章和后续章不能绕过最早待处理章继续生成。
- [ ] 文件缺失、为空、编码错误时显示修复提示，不提供覆盖原文的恢复动作。
- [ ] 候选稿生成不会改变当前正文的已完成步骤，也不会覆盖当前正文。
- [ ] 本地修改已接受正文后，本章回到复核流程，下游需复核状态可见。
- [ ] 接受成功而后续生成失败时，页面准确显示已接受结果及下一章失败。
- [ ] 重载或切换章节不会把项目运行状态误当成所选章节正在执行。
- [ ] 正文阶段没有通用「确认并推进」与逐章接受的重复入口。
- [ ] 窄屏、键盘和读屏可识别当前步骤、主操作与不可用原因。

实施时优先通过前端组件测试覆盖状态与按钮矩阵、刷新和接受时的版本变化、连续点击与章节切换；只有改变服务端行为或契约时才相应扩展后端测试。本设计文档本身不代表上述功能已经实现或通过验收。
