# 短篇爽文文风与创作问卷调整设计

日期：2026-10-24  
状态：已实现（2026-10-24）  
范围：移除新建项目的关系设定，新增文风选择，并将文风贯穿创作与审核。

## 1. 需求与决策

本次按以下要求设计：

1. 去掉新建项目问卷中的「关系设定」。
2. 增加「文风」，当前只有「短篇爽文」一个选项。
3. 将「基调」改名为「阅读体验」，与「文风」分别展示。

文风决定表达与叙事方法，阅读体验决定整体情绪。例如「短篇爽文 + 轻松」可以采用幽默反击，「短篇爽文 + 暗黑」可以采用冷峻复仇。文风不覆盖作者已选的类型、阅读体验、视角、篇幅及避雷约束。

「去掉关系设定」指移除问卷中的 `extras.relation` 输入，不删除人物关系阶段、关系产物及其生成能力。言情作品仍然需要人物关系，只是不再要求作者在创建时预选「青梅竹马」「敌对转爱」「重生追妻」等模式。

本文为实施依据；开发进展与验证结果见文末。

## 3. 页面交互

### 3.1 新建项目

保留现有布局与控件样式，基础字段包括：

| 字段 | 行为 |
| --- | --- |
| 项目标题 | 沿用现有行为 |
| 篇幅 | 沿用当前短篇选项 |
| 阅读体验 | 由原「基调」改名；保留轻松、热血、治愈、暗黑、紧张、厚重及自定义能力 |
| 叙事视角 | 保留现有选项 |
| 文风 | 仅显示「短篇爽文」，默认选中，不允许取消或自定义 |
| 人物数量 | 保留现有选答行为 |
| 其他类型专属问题 | 保留；仅删除言情的关系设定问题 |

文风作为独立通用问题，建议放在叙事视角之后、人物数量之前。可附简短说明：

> 语言直白，冲突前置，推进紧凑，反击有实际结果。

右侧问卷摘要同步新增「文风：短篇爽文」，删除「关系设定」行。更换小说类型时，文风保持选中；其他类型级联答案沿用原清理逻辑。

不增加「番茄风格」选项，不增加复仇、搞笑等风格分支。那些方向可以由阅读体验、创意和故事设定共同表达。

### 3.2 项目展示

有文风配置的项目展示文风名称。旧项目缺少文风时显示「未指定」，不得显示为短篇爽文，避免将新能力误描述成历史项目已经使用的能力。

第一版不提供创建后切换文风的入口。作者编辑正文仍沿用现有流程，系统不自动改写既有稿件。

## 4. 共享契约与数据存储

### 4.1 字段定义

在 `shared/src/index.ts` 定义文风 ID、标签、版本及 zod schema，以下为示意：

```ts
export const WRITING_STYLES = ['short-satisfying'] as const;

export const WritingStyleSelectionSchema = z.object({
  id: z.literal('short-satisfying'),
  version: z.literal('v1'),
});

// QuestionnaireAnswers 的新增字段，选填用于兼容历史数据。
writingStyle?: {
  id: 'short-satisfying';
  version: 'v1';
};
```

问卷的选项值为 `short-satisfying`，显示名为「短篇爽文」。前端将选项映射为上述结构提交；服务端验证 ID 与版本，不接受客户端传入自定义规则文本。

「阅读体验」是原「基调」的展示名称调整，本次不改变现有选项含义。内部字段继续使用 `tone`，不新增重复字段；原必答四项 `genre/length/tone/pov` 保持不变。新建页、问卷摘要、项目详情、缺失项提示及面向作者的说明统一使用「阅读体验」。内部提示词需明确它表达作者期待的整体情绪，避免误解为另一套文风。文风在新建项目中始终有值，但不直接加入通用必答列表，否则旧项目续跑时会因缺字段失败。

### 4.2 新建与历史项目的区别

- 新建项目：前端默认提交文风；兼容旧调用方，服务端仅在创建时为缺失文风补充 `short-satisfying/v1`，再存入 `Project.answers`。
- 已有项目：读取、续跑和种子修改不自动补文风；缺失时继续使用通用写作策略。
- 显式非法 ID、非法版本或错误结构：返回校验错误，不降级或自动替换。
- 问卷版本递增为 `v2`，新建项目写入新版；不批量更新旧项目版本或答案。

默认值不能定义在所有历史读取共用的 schema `.default()` 中，避免读取时悄悄改变旧项目语义。创建入口完成归一化，其他入口只做解析与校验。

文风随答案保存为 JSON 字符串，写入和读取均通过 schema 校验。本次不需要数据库迁移。

### 4.3 关系设定兼容

新问卷不再返回 `extras.relation`，新前端不提交该值。服务端创建入口清除旧客户端传来的 `extras.relation` 后再持久化，确保新项目不再带有已删除的问卷项。

历史项目已有的 `extras.relation` 不删除。旧项目再次生成或修改种子时仍遵守原作者选择，避免无意改写已确认关系；历史详情如有展示需要，可标注为旧版创作约束。其他 `extras` 项不受影响。

## 5. 文风规则管理

后端新增集中的版本化文风定义与解析器，例如：

```text
backend/src/novel/writing-style/
  writing-style.registry.ts
  writing-style.registry.spec.ts
```

解析器根据 `id + version` 返回各阶段需要的规则。规则由服务端维护，通过现有 `PromptRegistry` 注入各阶段模板，不在业务服务里散落拼接提示词，也不增加模型调用。

`v1` 发布后规则保持不可变；规则调整发布新版本并保留旧版本解析能力。项目保存的版本保证后续章节采用同一套规则，不通过修改同名预设影响历史项目。本次无需引入自定义文风编辑器、外部 MCP、检索库或模型微调。

### 5.1 短篇爽文 v1

| 方面 | 可执行要求 |
| --- | --- |
| 表达 | 白话清楚，以短句、短段为主；保留必要描写，避免句式机械一致 |
| 开篇 | 尽早呈现主角处境、具体冲突和期待，不长篇介绍背景 |
| 推进 | 优先通过行动、对话、选择揭示信息；压缩重复争执和心理解释 |
| 主角 | 面对冲突有选择和行动，行动逐步改变处境 |
| 情绪 | 阻力与损失具体可感，适时回应读者期待，避免持续受辱却无进展 |
| 爽点 | 反击带来可观察后果，例如利益追回、骗局揭穿、控制解除、局势逆转 |
| 反转 | 有信息或行动铺垫，符合人物能力、世界规则和已知事实 |
| 对手 | 有合理动机和应对能力，不能依靠集体降智制造胜利 |
| 结局 | 解决主要冲突，兑现核心期待，交代关键后果 |

以下不是规则：强制第一人称、固定字数内必须打脸、每章必须反转、每个角色必须震惊、结局必须留悬念、主角必须靠身份揭露获胜。

类型、视角、阅读体验、避雷、已确认设定和事件因果构成边界，文风在边界内调整表达与节奏。例如悬疑保持必要的不确定性，历史题材的反击遵循其制度环境。

## 6. 各阶段接入

### 6.1 种子生成与种子修改

种子阶段注入故事层面的文风规则：开篇目标具体、阻力清楚、失败代价明确，冲突能够通过主角行动推进并产生回报。优先复用现有 `storyEngine`，不新增一套重复的爽点产物 schema。

模型不得重新选择文风，不在种子结果里生成文风字段。风格是作者输入约束，继续放在问卷答案中。

种子修改也必须解析并注入相同文风版本。不能只更新首次生成模板，导致修改后的种子丢失创作方向。

### 6.2 世界观、人物与人物关系

保留现有阶段和产物结构。世界观不因追求爽感无限扩张设定；人物应有目标、能力边界和可行动的动机；关系发展仍由人物设定、种子及上游产物推导。

这几阶段仅接收必要的故事约束，不注入短句、短段等正文表达要求，避免结构化产物变成口号或正文片段。实施时检查各生成器的显式变量映射，不能仅假设新增 answers 字段会自动进入所有模板。

### 6.3 大纲

全书规划明确冲突升级、反击铺垫、高潮结果与最终回报。章纲在现有主要事件、冲突、结果和后续影响字段中体现这些内容，不新增节拍阶段或要求每章固定数量爽点。

过渡章可以承担铺垫和关系变化，但需要说明其对后续的作用。结局章完成兑现，不强制悬念。

### 6.4 正文

正文生成与候选稿生成使用同一版本文风。已有 `answers` 传参不能替代明确的规则段：模板需显式解释选定文风，并注入该阶段规则。

正文规则示例：

> 优先通过人物行动和对话展现冲突。反击发生时写清过程、对方反应和实际后果，不用「众人震惊」替代场景。避免重复解释已经清楚的情绪与信息，保持符合作者指定阅读体验的语气。

文风不能授权模型改变已确认章纲中的关键事件或结局。重生成仍另存候选稿，采用时沿用现有本地合并流程，不新增自动覆盖能力。

### 6.5 审核与摘要

审核复用七维结构，按相同文风版本细化判据：

| 维度 | 文风相关检查 |
| --- | --- |
| pacing | 是否过度铺陈、重复争执、行动停滞 |
| hook | 开篇与章末是否符合本章功能，建立的期待是否得到承接 |
| aesthetic | 是否表达直白清楚，避免空泛情绪、口号和重复套话 |
| character | 主角行动和对手反应是否符合动机及能力 |
| consistency / continuity | 反转和反击是否符合设定与前文事实 |
| foreshadow | 关键翻盘是否有必要铺垫，线索是否被合理回收 |

风格偏差默认属于建议性 `warning`；只有形成明确的节奏、人物或逻辑问题时才依现有规则提高严重度，不因「不够爽」直接阻塞接受。所有问题仍需引用正文证据，不新增无依据的爽感分数或固定通过分数。

事实摘要不追求爽文语气，继续记录实际发生的事件与持续变化，不因文风推断人物动机或新增事实。

## 7. 版本与已有产物

所有被修改的提示词模板提升版本。生成与审核规则从同一个文风定义解析，避免标准相互矛盾。

正文依赖指纹在有文风时增加 `{ id, version }`。无文风的历史项目仍使用原有指纹输入与序列化结构，不通过新增 `null` 或空对象改变旧指纹。

第一版文风创建后不可切换，因此没有中途切换带来的自动失效操作，也不重算历史项目的产物。未来开放切换时，需要单独设计上游重生成、正文复核和作者确认范围，不能只修改问卷字段后继续沿用旧审核结论。

## 8. 验证与验收

### 8.1 自动化验证

- 契约：接受唯一合法文风；拒绝非法 ID、版本与结构；旧答案仍可解析。
- 创建：缺省文风仅在新建入口补齐；持久化为固定版本；剔除新请求中的旧关系项，保留其他 extras。
- 问卷：所有类型均包含文风且无关系问题；四项必答及其他级联项行为保持一致。
- 前端：文风默认选中并实际提交；更换类型后保持；摘要显示文风且不显示关系设定。
- 历史兼容：无文风旧项目可以读取、续跑与修改种子；已有关系约束继续有效；历史指纹不变。
- 提示词：种子生成、种子修改、大纲、正文和审核都解析同一文风版本；作者已选视角与阅读体验不被覆盖；摘要不注入表达规则。
- 正文：有文风项目的依赖指纹包含版本，候选稿仍另存，不改变已有接受机制。

开发完成后运行受影响的单测与 HTTP 测试，并按项目要求完成 `npm test`、`npm run lint`、构建及格式检查。

### 8.2 样稿验收

测试通过说明链路正确，不等于文风达标。选取固定输入，对比通用策略与短篇爽文策略的种子、大纲及正文，至少覆盖：

1. 都市 + 轻松：反击可以幽默，但行动和结果清楚。
2. 言情 + 暗黑：无关系预选仍能生成合理关系；爽感不强行变成喜剧。
3. 悬疑 + 紧张：保持推理、信息控制和反转铺垫，不靠无依据能力解决问题。

人工比较开篇进入冲突的速度、无效铺陈、主角能动性、反击后果、结局兑现及人物逻辑。每项结论指向具体文本，不以模型自评或字数指标代替阅读判断。产生真实模型调用费用的样稿运行在实施验收阶段执行，本设计不声称已验证效果。

## 9. 实施顺序

1. 增加共享文风契约，明确新建默认与历史解析的区别。
2. 增加版本化文风定义与解析器。
3. 删除关系问卷项，增加文风题，更新创建归一化与问卷版本。
4. 更新前端默认值、答案转换、摘要与项目展示，将原「基调」统一改为「阅读体验」。
5. 接入种子生成、种子修改、上游生成器、大纲、正文及审核；提升模板版本。
6. 补正文指纹兼容与回归测试。
7. 更新当前有效规范和说明文档，执行自动化验证及样稿验收。

OpenSpec 可按需使用，不是实施前置条件；如更新规范，仅调整当前有效规范，不改写归档变更。

## 10. 完成标准

- 新建页面没有关系设定，文风只有默认选中的「短篇爽文」，原「基调」统一显示为「阅读体验」。
- 创建后的文风配置可追溯且被实际用于生成与审核。
- 旧项目不被自动改风格，旧作者约束与已确认产物保持兼容。
- 人物关系阶段、正文候选稿和作者编辑流程正常。
- 自动化验证通过，样稿体现预期写法且没有明显牺牲因果、人物和作者约束。


## 11. 实施验收记录（2026-10-25）

共享契约、问卷、页面、各阶段提示词、正文指纹与历史项目兼容已实现。构建和 lint 通过；前端 21 个文件、130 个测试逐文件通过（大纲组件测试使用 30 秒单例超时）；后端单测全量 35 个套件、299 个测试通过；HTTP 测试逐套件隔离运行，8 个套件、56 个测试通过。大纲测试中两处旧流程断言已按当前正文阶段行为更新。Node 24 在多个 HTTP 套件共用 Jest 进程时仍会触发 `better-sqlite3` 原生清理崩溃，因此未将该单进程命令的退出状态记为通过；逐套件运行均以退出码 0 完成。前端单进程全量复跑也曾遇到 Vitest worker 超时，逐文件复跑均通过。

真实模型对照及复验见 `docs/qa/writing-style-samples-2026-10-24.md` 与 `docs/qa/writing-style-samples-2026-10-24-xuanyi.md`。样稿中风格版更早进入冲突，但悬疑复验仍出现未给定的值班表，说明提示词不能保证消除虚构证据，作者仍需核对。当前审核规则已加入证据依据检查。
