# Design

## Context

动机与范围见 proposal.md。现有 `outline` 节点为占位，类型配置已有 8/40/200 章默认值。`StageContext` 不含关系，上游渲染也省略人物弧光、世界秘密和类型自定义设定。大纲需要两次人工确认，不能沿用“一次生成、一次确认即推进”的单步假设。

本方案以 `repair-pipeline-execution-safety` 完成后的运行所有权、StageRun 和阶段定义为基础。仓库可能存在该变更的进行中实现，是否可复用以其测试和验收结果为准，不能仅凭表或字段已出现判定依赖完成。

## Goals / Non-Goals

**Goals:** 维持主流程一个 outline 阶段，同时恢复其内部暂停点；结构和语义双重校验；按有效规划版本续跑，保护人工编辑；支持长篇分批产出。

**Non-Goals:** 场景节拍和正文生成、多人实时协作、无限版本历史、模型局部重写、章号拖拽重排。首版不保证自动判定文学质量或消除全部情节矛盾。

## Decisions

### 1. 用一个大纲阶段承载两个持久化步骤

内部流程：

```text
plan generation --> plan review --> chapter generation --> outline review --> confirmed
                          ^                 |
                          |                 v
                       plan edit      failed batch --> resume
```

流程图为示意；失败也可能发生于规划生成。内部步骤持久化为 `planning / plan_review / expanding / outline_review / confirmed`，错误、运行状态由 StageRun 及分段状态表达，避免步骤与失败状态组合爆炸。手动模式在 plan_review 与 outline_review 暂停；自动模式在每一步校验成功后自动确认并继续。

outline 节点内使用两个独立的图中断位置；确认请求带明确目标和内容版本。确认规划只恢复本节点，确认完整大纲才让通用阶段确认逻辑推进。恢复时从数据库内部步骤与内容版本重建判断，不只依赖 checkpoint 是否存在。外层 StageRun 在规划待确认时不能被视为整个大纲已确认。

不把全书规划拆成主流程新阶段，避免改变既有七阶段定义；不在收到任意 confirm 时直接推进，避免跳过章纲。已有其他阶段的确认请求保持兼容，大纲确认必须指定目标以拒绝迟到请求误确认下一步骤。

### 2. 共享契约与模型输出分开

先在 `shared/src/index.ts` 定义模型输出、持久化读取、配置和编辑请求 schema：

- `OutlinePlan`：主线、主要转折、高潮、结局、人物弧光、关键关系发展、按顺序排列的剧情段。剧情段包含稳定 id、标题、故事目标、核心事件、结果以及起止章号。
- `ChapterSummary`：章号、章名、所属剧情段、主要事件、参与人物引用、冲突、结果、后续影响；伏笔和关系变化可选。
- 大纲详情：目标章数、内部步骤、内容版本、规划版本、规划确认版本、完整确认版本、stale、规划、章纲、分批进度和错误摘要。
- `StageContext`：增加带数据库人物 id 的人物引用映射、关系，以及仅向下游提供的已确认大纲。保留旧生成器所需人物结构，避免强制改写无关模型输出。

目标章数独立于模型输出；省略时从 genre profile 的篇幅配置取默认值，服务端验证为正整数。用户改变目标章数属于规划变更。剧情段范围须连续覆盖 1..N；段内可再切成有界生成批次。

人物统一以当前项目有效人物 id 引用，提示词展示 id 与姓名，保存时验证引用；不凭模型新造 id 或仅按同名映射。结构 schema 之外还校验章节总数、连续范围、唯一性、人物与关系引用和版本来源。语义校验失败进入统一有界修复流程，耗尽后返回定位明确的错误，不无限重试。

### 3. 持久化内容与执行事实分离

新增 `Outline`（projectId 唯一）保存 targetChapters、step、revision、planRevision、planConfirmedRevision、confirmedRevision、planData、stale 及时间；新增 `OutlineBatch` 保存 outlineId、planRevision、起止章号、data、status、error、已知用量。结构化数据以 JSON 字符串存储，读写均校验；状态用 String。

有效规划下的批次以 `(outlineId, planRevision, startChapter)` 唯一，批次范围由程序切分，不由模型改变。每批暂定最多 10 章，长度与 token 预算配置在生成策略中；200 章也不要求单次输出。章纲存在所属批次 data 中，读取汇总排序；编辑章节时在事务中更新对应批次并增加大纲 revision。

规划保存后增加 revision 与 planRevision，清空确认，旧批次保留为失效回看数据。章纲编辑仅增加 revision，保持 planRevision，清空整体确认并使下游失效。全局 revision 用于编辑冲突，planRevision 用于批次来源，两者不能互相代替，否则修改一章会错误导致所有批次需重生。

StageRun 记录阶段执行与用量，Outline/OutlineBatch 记录内容与恢复进度，不在 checkpoint 内放整本章纲。批次内容、完成状态与对应已知用量累计必须原子提交；调用用量通过统一记录基础设施以唯一调用标识防止重复入账。

### 4. 顺序分批展开以控制上下文

先生成并校验完整规划，确认后按剧情段顺序展开，每段按批次顺序生成。每次传入作者问卷约束、种子、必要世界规则及类型块、人物弧光、关系、完整规划、此前已完成章节的精简摘要与当前批次目标。概要摘要由程序按字段裁剪，避免把整段历史全文重复拼入。

补齐 `UpstreamAssembler` 的关系映射及上游渲染。依赖声明包括 premise、characters、relations，以及类型未跳过时的 world；关系就绪依据 StageRun 确认状态，允许合法空集合。上游设定与人工编辑作为数据输入，不作为覆盖系统规则的指令。

注册两个带版本提示词，分别用于规划和章纲，复用模型注册、结构化输出、错误分类、取消信号及用量记录。已完成批次不再调用模型；失败批次从头重试且原子替换，不追加重复章号。已保存人工编辑进入后续批次上下文。

一次生成全部 200 章的方案实现简单，但输出预算与失败重做成本高；并行分批容易丢失前后因果，因此首版采用顺序分批。

### 5. API 操作显式区分保存和确认

建议 HTTP 契约，最终 schema 与类型均先定义于 shared：

| 方法与路径（前缀 /api/novel/projects/:id） | 作用 |
| --- | --- |
| GET /outline | 查询配置、内容、内部步骤、版本与批次进度 |
| PATCH /outline/config | 设置目标章数；已有规划时按规划变更使依赖失效 |
| PATCH /outline/plan | 按 expectedRevision 保存完整规划，不启动生成 |
| PATCH /outline/chapters/:number | 按 expectedRevision 保存单章，不改变章号与归属 |
| POST /confirm | 扩展可选 target 为 outline-plan 或 outline，携带 expectedRevision；其他阶段沿用原契约 |
| POST /generate | 沿用生成入口，默认从内部失败/未完成步骤续跑；force 明确表示从规划重新生成 |

GET /outline 在尚无大纲记录时返回默认配置和空内容，不产生写入；详情读取加入大纲概要与阶段状态，不强迫轮询每次返回长篇全部章纲。

更新与确认在事务中校验当前项目运行状态、expectedRevision、上游有效性、当前内部步骤。生成期间返回冲突，旧版本返回冲突，非法结构/引用返回校验错误。数据库条件更新检查影响行数，不做先读后无条件写。完整确认验证所有有效批次及全部章节后记录 confirmedRevision；下游只装配该版本。

重复确认同一版本与同一目标应幂等，不重复派发模型请求。迟到的规划确认不能被解释为完整大纲确认。自动模式使用相同的内部确认服务。

### 6. 接入统一运行保护和失效行为

每次批次写入同时验证项目 runId、planRevision 与有效步骤，并与内容写入处于同一数据库事务。模型调用携带取消信号；超时或服务重启后的旧运行即使返回，也不得提交状态、内容和错误。生成期间不接受人工编辑。

规划编辑、章纲编辑和上游回退的失效操作注册到阶段定义，禁止在控制器各自写一套级联规则。修改规划使所有章纲及下游失效，修改章纲保留其他章与规划并使下游失效。大纲已不在当前阶段时，首版要求先通过既有回退入口回到 outline 后编辑；回退沿用下游失效语义。

### 7. 桌面工作台编辑

在现有工作台加入大纲内部步骤区与目标章数配置。规划使用结构化表单，章节按剧情段分页或折叠展示，避免一次挂载 200 个编辑表单。保存和确认按钮独立；本地有未保存内容时阻止确认。规划修改影响已有章纲时告知失效范围。

失败时显示失败批次和已完成数量，提供续跑。生成中禁用编辑；编辑冲突保留本地输入并提示刷新核对。沿用桌面 1280/1440 视口范围，不扩展移动端适配。

## Risks / Trade-offs

- 两次暂停可能被通用确认误当作阶段完成 → 显式确认目标、持久化内部步骤与图恢复测试共同约束。
- 长篇总耗时超过原有整图超时 → 为大纲配置有界的单次模型、批次与总执行预算，达到预算保存进度并报告可续跑；不靠无限放大超时解决。
- 结构校验不保证文学连贯 → 提供全书规划、前文摘要、人工编辑与确认；不声称自动验收文学质量。
- 规划修改会丢弃较多可用章纲 → 保留失效内容供回看，首版以正确性优先，不做自动局部复用推断。
- 与安全修复并行修改同一流水线 → tasks 第一项先验收依赖，再基于实际阶段定义接口接入，避免复制锁与状态聚合。

## Migration Plan

1. 先验收执行安全修复；使用其新增模型与运行保护，不修改该变更的规划工件。
2. 增量迁移新增 Outline/OutlineBatch 表及 Project 关联，不改既有产物数据；旧项目按需读取默认配置，首次生成时创建记录。
3. 对过去停在 outline 占位失败的项目，没有有效规划时从规划生成启动；不清空无关 checkpoint，恢复入口按持久化业务步骤校准图位置。
4. 执行契约、迁移、恢复和运行安全回归后交付。回滚应用时保留新增表及内容，旧版本继续拒绝未实现的大纲；不采用删表回滚，避免丢失作者编辑。
