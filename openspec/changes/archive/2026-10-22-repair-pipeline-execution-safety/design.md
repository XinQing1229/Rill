# Design: Pipeline Execution Safety

## Context

当前项目以 `Project.status` 作为运行锁，状态检查与更新分离；图超时使用 `Promise.race` 返回失败，但底层任务仍继续。阶段状态部分由产物行聚合，因此无产物的失败和合法空集合无法准确表达。回退删除 checkpoint 后，已完成目标再次进入图时会触发幂等跳过并再次暂停。

## Goals

- 同一项目始终只有一个可提交结果的运行。
- 取消、超时、回退或重试后，失效运行不能提交状态或产物。
- 阶段状态独立于产物数量，支持失败、待确认和空集合成功。
- 依据明确的业务阶段状态恢复手动确认和回退。
- 将阶段存储行为集中定义，接入新阶段时不再扩散阶段分支。

## Design

### 运行所有权与隔离

以 `Project` 上的运行标识和状态版本作为运行租约。入口通过条件更新原子领取运行权；只允许持有当前标识的运行推进阶段或结束项目。回退等改变流程位置的操作仅允许在没有有效运行时执行。超时触发取消信号并使运行标识失效；模型调用和生成器接收 `AbortSignal`。即使底层提供方无法及时取消，所有持久化写入仍须验证运行标识，防止迟到结果污染新运行。

不能仅靠进程内锁，因为服务可能重启或未来运行多个实例。数据库条件更新是所有入口共同的互斥点。

### 阶段执行记录

新增阶段运行记录，按项目、运行标识和阶段追踪状态、错误、用量、尝试时间及确认状态。阶段记录表达执行事实；产物表表达结构化内容及失效标记。合法空集合可完成阶段而无需伪造产物行。API 将阶段状态与产物分开返回，前端按阶段状态展示失败、待确认及完成。

### 恢复与确认

明确区分开始生成、续跑失败阶段、确认推进、显式重生成和回退。手动确认使用已持久化的当前阶段及阶段状态来选取下一阶段；不把 checkpoint 是否存在作为业务判断。checkpoint 仍负责恢复图的内部执行位置。

### 阶段定义与存储适配

扩充阶段定义，统一声明依赖、状态读取/更新、产物查询与失效操作。`StageRunner` 与 `UpstreamAssembler` 通过阶段定义访问产物，避免各自维护相同的阶段分支。前端以 API 返回的阶段状态作为显示来源。

### 兼容性与迁移

新增表不更改已有产物格式。旧项目的阶段状态由现有产物行回填或在读取时兼容推导；对没有产物的既有失败项目，以 `Project.currentStage/status` 作为迁移初值。迁移应可重复部署，且保留 SQLite 数据和 LangGraph checkpoint。

## Risks

- SQLite 的条件更新必须检查受影响行数，所有入口统一经由同一获取运行权路径。
- 取消模型调用不保证底层立即停止，因此写入前的运行标识检查是必要保护。
- `StageContext` 目前不包含关系；新阶段定义应显式声明依赖和上下文映射，避免隐式查询。
- 迁移时旧的 running 项目需转为可续跑失败状态，不能误判为仍由有效运行持有。

## Out of Scope

- 多队列工作者、分布式调度、平台发布与正文生成功能。
