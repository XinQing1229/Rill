# Design

## Context

动机与范围见 `proposal.md`。当前 `PremiseGenerator` 仅根据项目题目和问卷调用注册提示词，并直接覆盖 `Premise.data`；`StagePanel` 负责种子展示和阶段操作，后续阶段回看也是同一面板。

`PipelineService.acquireRun` 通过项目 `updatedAt/status/runId` 条件更新获取执行权；`releaseRun` 在运行未收尾时会把项目标为失败，因此不能原样套用于只生成预览的任务。`StageRun` 与产物分开记录，确认字段为 `confirmedAt`。下游失效通过 `ArtifactRegistry` 和 `storageFor(stage).invalidate` 覆盖不同阶段，包括大纲/节拍版本确认及正文复核状态。

流水线 checkpoint 与 Prisma 产物分别持久化；现有回退先失效下游、删除 checkpoint，再修改当前阶段。候选采用需防止旧 checkpoint 继续旧的下游路径。自动模式目前在普通阶段完成时自动确认，前端普通确认按钮也仅在 manual 下显示，采用后暂停需要显式适配。

## Goals / Non-Goals

**Goals:**

- 将候选生成与正式产物写入隔离，失败时不破坏上一次成功候选。
- 复用项目执行互斥、AI 基建和阶段失效规则，同时保留预览前的项目执行位置和状态。
- 采用仅提交服务端持有的完整候选；重复采用不得再次回退。

**Non-Goals:**

- 不新增创作 Stage，不改变既有重新生成语义。
- 不做历史版本 UI、撤销恢复、字段 diff、候选上的连续调整、刷新恢复编辑会话。
- 不改问卷选择，不扩展至世界观/人物等其他阶段的建议修改。

## Decisions

### 1. 独立服务与契约

新增 `premise/premise-revision.service.ts`，由 `NovelController` 暴露两个接口：

- `POST /api/novel/projects/:id/premise/preview`：`{ requestId, feedback }`，返回 `{ candidateId, premise }`。
- `POST /api/novel/projects/:id/premise/adopt`：`{ candidateId }`，返回更新后的项目详情。

在 shared 先定义请求/响应 zod schema；`requestId` 使用 UUID，建议 trim 后为 1 至 2000 字符（实现默认限制）。候选按 `PremiseSchema` 校验；旧正式种子按 `PremiseReadSchema` 读取，因此历史无故事发动机的种子仍可作为修改基础。

复用 `PremiseView` 展示候选，不允许客户端直接传入候选 JSON 作为正式种子。放弃仅清除前端预览引用，不改变创作状态；不增加删除接口。独立接口避免把当前阶段生成参数扩展成种子专用分支，亦允许从后续阶段预览而不先回退。

### 2. 服务端候选与请求去重记录

新增项目关联的候选请求存储（如 `PremiseRevision`）：请求 UUID、项目 ID、建议、状态、可空候选 JSON、基础种子指纹、采用时间、错误及用量字段；项目内请求 UUID 唯一，候选 ID 为服务端标识。结构化内容以 JSON 字符串保存，读取时校验，不使用 Prisma Json/enum。

每轮创建独立请求记录；生成成功才保存候选并返回，新一轮失败不修改之前成功记录。UI 保留上一次成功候选 ID。采用时间提供重复采用的去重凭据；已采用 ID 再次提交只返回当前项目，不再次回退。记录服务于候选核验和去重，不提供历史版本恢复功能；项目永久删除时级联清理。

同一请求 ID 的重复生成：已成功则返回已有结果，进行中则返回冲突，已失败则返回该失败；用户显式重试创建新 ID，传输重试沿用原 ID。不同 ID 同时提交仍由项目锁拒绝并行调用。相比仅内存锁，这能覆盖多页面和响应丢失后的重试。

基础指纹用于服务端核验候选仍对应当前正式种子；不引入通用版本编辑系统。若正式种子已被其他操作替换，拒绝采用并保留前端建议和预览供查看，提示重新生成。此为避免保存已过期候选的实现一致性保护，不扩展为冲突合并功能。

### 3. AI 输入与用量

在提示词注册表新增种子修改模板，例如 `premise-revision/v1`；输入为项目题目、类型画像、原始问卷约束、当前正式种子、当次建议。要求按建议修改相关内容，必要时同步相关字段保持一致，其他内容尽量保留；不把原种子或建议中的文本当成改变系统规则的指令。输出完整种子，复用 `LlmService.completeStructured`、错误分类与 `UsageRecorder`。

每轮始终从正式种子生成，不使用旧候选。模型调用成功/失败均按现有可取得的用量累计到项目并记录本次请求用量；候选生成不改正式种子的生成用量和阶段确认，避免成本被重复归入原产物。

### 4. 共用项目执行权，预览不运行图

提取/复用 `acquireRun` 的条件更新机制，使流水线、预览生成和采用互斥，不另设只在进程内生效的锁。预览持锁期间项目可暂时为 running，但不得改变 currentStage、StageRun 或 checkpoint；前端以卡片的生成中状态说明当前动作。

生成前保存项目原状态，结束时仅由持有同一 runId 的任务恢复原状态并释放锁；失败也不能把原来 idle/done/failed 的创作项目误标成一次流水线失败。预览使用超时/取消和持锁核验写入，过期任务不得提交，错误记录在修改请求而非正式种子。超时恢复须覆盖新任务类型，不能遗留永久 running 的项目。

采用前也领取同一执行权，并在锁内检查候选归属、状态、采用凭据及基础指纹。生成期间采用旧候选同样被禁止。已有模式切换、回退、删除等冲突操作继续遵守项目运行保护。

### 5. 采用与推进位置

采用不调用 `generate(force)` 或执行普通种子生成节点，避免重复调用模型、提前使下游失效或自动模式立即向下推进。

持有项目执行权后先清除旧 checkpoint；失败时不提交正式产物。清理成功后，在同一 Prisma 事务内：

1. 再核验运行归属与候选有效性。
2. 写入候选到正式种子，置 done、stale=false、清除错误。
3. 失效旧种子阶段执行记录并建立未确认的有效记录，确保上游装配读到新内容；不遗留有效的旧 confirmedAt。
4. 按 `stagesFor` 对下游 StageRun 与 storage 适配执行失效，撤销对应确认；保留正文文件。
5. 更新 currentStage=premise、status=idle，保留原 mode，标记候选已采用并结束本次运行。

将现有下游失效能力补充为可在指定事务中调用的内部路径，避免各阶段分开提交。checkpoint 不在 Prisma 事务内，故始终先清理、后提交；若清理成功而事务失败，正式内容不变，现有无 checkpoint 的确认分支可按 currentStage 推进。重试清理应幂等；不得先报告采用成功再异步清理。

采用后不调用图，manual/auto 均待显式确认。前端在种子有效、未确认且项目空闲时提供确认入口，包括采用后的 auto；确认复用现有 `confirm` 的无 checkpoint 分支，从下一阶段开始，随后按原 mode 推进。后端确认仍为最终判断依据。

### 6. 卡片与失败保留

新增 `PremiseRevisionCard`，在 `StagePanel` 的正式种子及阶段操作之后渲染，仅有有效种子时可发起。通过项目 ID 隔离输入和候选状态，避免切项目串数据。

前端分别管理 `feedback`、`lastSuccessfulPreview`、错误和请求状态；开始生成或请求失败均不清空输入和旧预览，仅成功响应替换预览。重新生成按钮文案明确基于正式种子。编辑建议不篡改已展示候选；采用始终针对可见的候选 ID。放弃清除候选展示，建议保留以便调整。

提交瞬间设置同步防重保护，并禁用生成、采用和其他冲突操作；后端 409 时显示错误并刷新项目状态，保留输入和预览。采用失败同样保留现场；成功后清除已采用预览，刷新工作台，显示种子待确认及下游失效。采用前确认提示按实际已存在的下游阶段列出影响。

## Risks / Trade-offs

- [预览锁使项目暂时显示 running] → 卡片显示具体动作，结束恢复原状态；不写正式阶段 generating，不污染时间轴。
- [运行失败收尾复用不当造成项目被标 failed] → 为预览实现专用收尾并测试成功、失败、超时及过期任务提交。
- [旧候选响应晚到或跨项目串数据] → 请求身份与项目 ID 校验；切换项目隔离状态，不接受过期响应覆盖最新预览。
- [checkpoint 与产物无法共事务] → 持锁先清快照再事务提交，测试清理失败、提交失败及之后确认的恢复行为。
- [auto 模式普通完成逻辑自动确认] → 采用绕过生成节点，明确创建未确认状态；测试采用前后模型调用次数与确认后的继续位置。
- [工作区已有大量未提交改动] → 实施以当前源码为基线，限定改动到本 change 的功能，避免覆盖既有正文、导出等工作。

## Migration Plan

新增候选请求表和项目级关联迁移，已有项目与种子不回填、不改写。部署后执行 Prisma generate，再构建 shared/backend/frontend。

回退功能时先移除新卡片与接口，保留新增表即可兼容旧代码；已采用的种子继续作为普通正式种子保留，下游失效不自动撤销，避免恢复不再匹配的内容。
